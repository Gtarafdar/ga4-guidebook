# Data Governance & Cardinality

Controlling what data GA4 collects, keeps, and how well it holds up under scale. Numbers below are last-known and worth reconfirming at support.google.com/analytics for anything high-stakes — Google changes limits over time.

## Cardinality
Cardinality is the number of distinct values a dimension takes on. When a dimension exceeds roughly 500 distinct values in a single day, GA4 starts grouping the least-frequent values into an **(other)** row rather than showing every individual value. Standard reports are also capped at roughly 50,000 rows per day; beyond that, GA4 keeps the top rows by the report's metric and folds the rest into (other).

*Business use:* if you see a large, growing "(other)" row eating an increasing share of a report, the underlying dimension is too high-cardinality for reliable reporting — commonly a mistake like sending full page URLs (with unique query strings/IDs) into a custom dimension meant for something categorical like page type.

## Custom dimensions/metrics limits
Roughly 50 event-scoped and 25 user-scoped custom dimensions, plus 50 custom metrics, per standard property. Event parameters themselves are limited to roughly 20-25 usable slots per event — parameters beyond that are silently dropped with no console error.

*Business use:* audit what's actually being sent in event parameters periodically; it's easy to silently exceed the parameter slot limit as tracking accumulates over time, and there's no error to alert you.

## Data retention
Two options for how long user-level and event-level data is retained for use in Explorations and funnel-style reports: 2 months or 14 months (GA4 360 extends this further, up to 38-50 months). This setting does **not** affect standard aggregated reports, only Explore-style analysis and funnels that need raw event-level data.

*Business use:* set retention to 14 months from day one on a new property if you'll ever want year-over-year exploration — this can't be applied retroactively to data already past the shorter window.

## Filtering data in/out
**Internal traffic filters** exclude known internal IP ranges (office, VPN) from reports so employee activity doesn't pollute real user data. **Developer traffic filters** exclude events generated by debug/testing devices. Both are configured in Admin > Data Settings > Data Filters, and can be run in "Testing" mode before switching to "Active" so you can verify the filter catches the right traffic before it silently starts excluding data.

*Business use:* set these up before a big campaign or launch, not after — you can't retroactively exclude internal traffic from data that's already been collected and counted.

## Data deletion & privacy
Users can request deletion of their own data; GA4 supports data deletion requests via the Admin API for compliance with regulations like GDPR/CCPA. GA4 also anonymizes IP addresses by default (no configurable IP anonymization toggle needed, unlike Universal Analytics).

*Business use:* if legal/compliance asks "can we delete a specific user's data on request," the answer is yes via the Data Deletion Requests API — this is a real, supported workflow, not something to build custom tooling for from scratch.
